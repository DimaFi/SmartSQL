# План развития SmartSQL

Обновлён 14 октября 2026. Это порядок будущей работы и критерии готовности. Фактическое состояние: [матрица возможностей](CAPABILITY_MATRIX.md); архитектурные решения: [DECISIONS.md](DECISIONS.md). Перечисленные будущие функции не считаются реализованными.

## 1. Финальная цель

Универсальный desktop-клиент для структурированных данных в направлении DBeaver: подключение к разным СУБД, изучение таблиц, работа с данными, запросы, обмен и перенос через единое понятное рабочее место.

Целевая версия включает:

- SQLite, PostgreSQL, MySQL/MariaDB и SQL Server с общими сценариями и явными различиями возможностей.
- Два полноценных режима: работа с таблицами для пользователей Excel и расширенная работа с SQL/структурой.
- CSV/JSON/XLSX, перенос между провайдерами и безопасные изменения структуры с отчётом о несовместимости до записи.
- Локальные и внешние резервные копии с проверенным восстановлением; облачные диски и личные серверы как дополнительные места хранения.
- Локального помощника через Action/Permission, подтверждения и аудит; без произвольного SQL-доступа модели.
- Дипломный сценарий педагогической практики на универсальном ядре, пригодном для других предметных областей.

Полезные версии выпускаются до завершения всех пунктов. ИИ, остальные СУБД и облачные копии не являются условием первой удобной версии PostgreSQL/SQLite.

## 2. Подтверждённые приоритеты

1. Ближайший большой результат — удобная и стабильная работа с PostgreSQL и SQLite.
2. Оба режима важны: выбор при первом запуске, запоминание выбора, постоянная кнопка переключения.
3. Для нескольких баз выбираем одно основное окно с деревом подключений и вкладками. Отдельные окна подключений сейчас — промежуточная реализация.
4. Сначала полноценный русский интерфейс, затем полный английский перевод.
5. Внешний вид доводим по двум присланным референсам вместе с функциями: тёплая светлая тема, зелёный акцент, аккуратные таблицы и единые диалоги.
6. Календарного дедлайна нет. Работа делится на небольшие проверяемые этапы; даты выпуска появятся после оценки конкретного объёма.
7. Всё создаваемое проектом — на D:. Локальные данные, копии, веса и результаты тестов — вне Git; проверенные этапы коммитятся.
8. Облачные диски и личные серверы для копий — последующий этап после устойчивой работы с внешними базами.

## 3. Исходная точка

Код `f57751c`: SQLite-проект SmartSQL, CRUD, фильтры, копии/восстановление, CSV/JSON/XLSX и вставка из Excel; PostgreSQL-профили, каталог, страницы, текстовый поиск/сортировка и явно разрешённое изменение одной ячейки по PK.

Предыдущая проверка: Debug-сборка без предупреждений; **330 тестов**, включая **20 PostgreSQL-проверок**, без пропусков. Тестовый кластер PostgreSQL 17.2 находится на D:. Новый диалог изменения PostgreSQL ещё требует ручного прогона пользовательского сценария.

Пробелы исходной точки `f57751c`: обычный чужой SQLite-файл пока не открывается через общий обозреватель; PostgreSQL пока не добавляет/удаляет строки; внешний обмен, SQL-редактор, общие вкладки, связи, смена типов, другие провайдеры и встроенный ИИ пока не готовы. Текущий обмен работает с управляемыми таблицами SmartSQL, а не с произвольной внешней БД.

На текущем этапе реализовано: PostgreSQL добавляет одну строку по отдельным возможностям INSERT и удаляет одну подтверждённую строку через независимые DELETE-возможности; обычный SQLite открывается для чтения через общий обозреватель. DELETE пока запрещён при любом входящем FK; расширение RESTRICT/NO ACTION требует отдельной защиты child-метаданных/прав. Проверка текущего этапа — Debug без предупреждений, 374 теста (1/113/260), включая 41 PostgreSQL-проверку, без пропусков. Общий интерфейс вкладок и внешний обмен остаются следующими задачами. Ручная приёмка нового UI пока открыта.

Для продолжения в новом чате используются [TASKS.md](TASKS.md) и [HANDOFF.md](HANDOFF.md). Общий план и 25 задач для GitHub подготовлены в [github-issues.json](github-issues.json); они ещё не созданы. Пользователь добавил SmartSQL в доступ плагина, но последующая проверка вернула сетевую ошибку сервиса; вход обычного Git не завершён. По просьбе пользователя публикация отложена, работа идёт локально. Повторять вход/публикацию по следующему запросу; результат подтверждать URL задач и удалённым SHA.

## 4. Ближайшие задачи

| Порядок | Работа | Критерий готовности |
| --- | --- | --- |
| N0 | Приёмка текущего PostgreSQL-редактирования | На тестовых данных проверены чтение/запись, NULL/пустота, запреты, сохранение, конфликт, отмена и закрытие. Ошибка загрузки после сохранения не скрывает состоявшуюся запись. |
| N1 | Добавление одной строки PostgreSQL — код/автопроверки готовы, UI — N0 | Отдельные INSERT-возможности и required/default/identity/generated метаданные. Различаются «заполнит сервер», NULL и значение. Ошибка откатывает вставку; результат возвращает реальные значения/ключ. Неизвестный COMMIT не повторяется автоматически. |
| N2 | Удаление одной строки PostgreSQL — первый срез проверен, UI — N0 | Отдельные DELETE-права, проверка полного ключа/версии/структуры и подтверждение строки. Первый вариант блокирует пользовательские DELETE-триггеры/правила и все входящие FK. Удаляется ровно одна строка либо ничего. Поддержка входящих RESTRICT/NO ACTION требует отдельного расширения T06/T12. |
| N3 | Обычный SQLite через общий обозреватель — код/автопроверки готовы, UI — N0 | Сначала чтение чужой базы: каталог, типы, ключи, страницы. Метаданные SmartSQL не добавляются, исходная база не мигрируется. Ограничения динамических типов SQLite видны. |
| N4 | Общее окно и вкладки PostgreSQL/SQLite | Подключения/таблицы сохраняют собственное состояние. Команда действует на активную вкладку; одинаковые имена разных баз не путаются. Закрытие корректно завершает её операции. |
| N5 | Фильтры по типам и нативная сортировка | Числа/даты сравниваются по типам. Условия текста/чисел/дат/Boolean/NULL применяются до пагинации. Неподдерживаемая операция объясняется, не подменяется текстовым сравнением. |
| N6 | Ограниченное редактирование обычного SQLite | После стабильного чтения — изменения по подтверждённым ключам с проверкой структуры/исходных значений, транзакциями и копиями поддерживаемых локальных файлов. NULL и динамические типы проверяются отдельно от правил проекта SmartSQL. |

N0 — приёмка UI; независимый SQLite-обозреватель и анализ INSERT-метаданных могут разрабатываться параллельно. INSERT/DELETE не наследуют права и политику UPDATE: отдельно проверяются DEFAULT-функции/sequence-права и входящие FK/каскады. N4 зависит от правил владения подключением и состоянием вкладки; N6 — от N3. Массовые изменения и общая отмена внешних записей идут отдельными срезами.

## 5. Большие этапы

| Этап | Результат для пользователя | Приёмка |
| --- | --- | --- |
| A. Удобный PostgreSQL/SQLite | Нативный просмотр, поддерживаемые добавление/изменение/удаление, фильтры/сортировка и общее рабочее место | Закрыты N0–N6 для заявленных возможностей; полный пользовательский сценарий проходит без потери данных, конфликтных перезаписей и смешивания подключений. |
| B. Два режима и завершённый русский UI | Выбор при первом запуске, постоянный переключатель, простой сценарий без SQL и расширенные инструменты | Переключение сохраняет вкладку/условия. Все диалоги/статусы на русском. Основные действия доступны с клавиатуры, при изменении размера/масштаба. Дизайн сверён с референсами. |
| C. SQL и структура | SQL-вкладки, подсветка, запуск/отмена, результаты/сообщения, локальная история/сохранённые запросы; PK/FK/индексы/ограничения | Первая версия использует серверный режим чтения, лимиты и отмену. Проверены попытки записи через CTE/несколько команд, большие результаты и закрытие. История/SQL-файлы не отправляются в Git автоматически. |
| D. Обмен с внешними таблицами | Сначала экспорт таблицы/результата, затем импорт CSV/JSON/XLSX и вставка Excel через общий мастер | Область выгрузки названа явно. Типы, NULL/пустота, большие числа, даты/timezone и binary не теряются молча. Импорт показывает сопоставление, несовместимость и preview до атомарной записи. |
| L. Полный английский интерфейс | После приёмки русского PostgreSQL/SQLite — полноценный выбор языка для тех же сценариев | Совпадают ключи RU/EN; переведены диалоги, статусы, ошибки и диагностики. Нет смешения языков и изменения самих значений из-за локали. Далее новые функции сразу поддерживают оба словаря. |
| E. Новые СУБД | MySQL и MariaDB, затем SQL Server в том же рабочем месте | Каждый провайдер проходит «подключение → каталог → чтение → разрешённые изменения → обмен» на реальной тестовой СУБД. Ограничения записаны в матрице; поддержка типов не обещается одинаковой. |
| F. Структура, связи и перенос | Связанные записи, безопасная смена типов, поддерживаемое изменение структуры и перенос между провайдерами | До записи есть отчёт затронутых данных/зависимостей и совместимости, а также проверенный способ восстановления. Ошибка не оставляет частичный результат. |
| G. Action/Permission и помощник | Структурированные действия, разрешения/аудит, затем помощь словами | Action/Permission проверен до модели. Помощник объясняет изменения и подтверждает запись; выполняются только разрешённые действия. Неподдерживаемый запрос не исполняется догадкой. |

B развивается вместе с A; доводка UI продолжается на C–F. Изучение PK/FK для N1/N2 предшествует полному инспектору C. Совместимость проверяется уже в D и каждом новом провайдере. Безопасная смена типов локального проекта может стать отдельным небольшим шагом до полной межпровайдерной миграции.

После фильтров и обмена отдельно добавить быстрые расчёты (количество, сумма, среднее) и простые графики по поддерживаемым типам. Проверять область расчёта — текущий результат или вся таблица — и точность чисел. Форматирование SQL, планы выполнения и дополнительные редакторы значений развивать небольшими расширениями C; инструменты появляются в интерфейсе после реализации.

Ручной SQL — самостоятельная функция опытного пользователя. Проверка первого слова SELECT недостаточна: режим чтения и права задаёт провайдер. Пользовательские функции не объявляются полной песочницей внешних побочных эффектов. Произвольная SQL-запись, длительные ручные транзакции и общая отмена внешних операций требуют отдельного решения и проверок.

## 6. Будущий интерфейс и расширение

Ориентир — дерево подключений/объектов в [DBeaver](https://dbeaver.com/docs/dbeaver/Database-Navigator/) и дерево слева с вкладками рабочего места в [pgAdmin](https://www.pgadmin.org/docs/pgadmin4/latest/user_interface.html). Это выбранная схема SmartSQL.

```text
Верх: открыть / подключить / импорт / действия активной вкладки / переключить режим
Слева: подключения → базы/схемы → таблицы/представления
Центр: вкладки таблиц и SQL; основная площадь — данные и результаты
Справа: сворачиваемые структура / свойства / ограничения объекта
Снизу: активное подключение, чтение/запись, результат и состояние загрузки
```

В простом режиме — таблицы, поиск, фильтры, записи и понятный импорт. В расширенном — те же данные плюс SQL, подробная структура, история и готовые дополнительные инструменты. Переключение меняет детализацию, а не подключение и не разрешение записи.

Группы команд: подключения, данные, запросы, импорт/экспорт, структура, копии/восстановление, настройки. У действия — единая подпись, обработчик, доступность и горячая клавиша, если нужна. Общие стили/иконки/ресурсы отделены от бизнес-операций. Кнопки будущих функций появляются вместе с рабочими сценариями.

После каждого нового сценария проверяются размеры/отступы/шрифты, таблицы, пустые/ошибочные/загружаемые состояния, фокус и читаемость. Приёмка включает обычное/минимальное окно, масштаб 100/150/200%, длинные названия и путь с клавиатуры. Иконки-кнопки, таблицы и вкладки имеют доступные имена/роли; ошибки, NULL и запрет записи обозначаются текстом, а не только цветом. Проверяются контраст, возврат фокуса после диалогов и короткий сценарий с экранным диктором Windows, включая сообщения результата/ошибки. Скриншоты сравниваются с пользовательскими референсами; управление ПК в текущей сессии запрещено.

Английский вводится после полного извлечения русских строк диалогов, статусов, валидации и провайдерных диагностик. Нужны совпадение ключей RU/EN, отсутствие смешения языков, корректное форматирование без изменения значений. Для первого перевода допустимо применять язык при следующем запуске.

Модель развивается отдельно в [DimaFi/SmartSQL-ML](https://github.com/DimaFi/SmartSQL-ML). Единственное рабочее место для всего ML — `D:\Code\SmartSQL-model`; внутри него остаются source, docs/scripts, datasets/профили, веса, эксперименты, кэши и временные/test/benchmark результаты. Самостоятельные скрипты сборки/тестов и изоляция пакетов подготовлены; 9 существующих тестов используют stub-ответы. Это не интеграция реальной модели или обучение. Главный приоритет PostgreSQL/SQLite и граница Action/Permission сохраняются.

## 7. Копии на облачных дисках и личных серверах — позже

После устойчивых внешних сценариев; независимо от готовности ИИ:

1. Определить объект копии: локальный проект или восстановимый снимок конкретной серверной БД. Экспорт таблицы не называется копией всей базы.
2. Проверить согласованное создание, целостность и восстановление для заявленного провайдера.
3. Начать с папки облачного клиента и сетевого/серверного хранилища; прямые API/протоколы выбирать по конкретной потребности.
4. Настройки: назначение, путь/адрес, профиль доступа, расписание, число версий/срок хранения, проверка результата.
5. Сначала создать проверенную локальную копию, затем передать её в хранилище. Ошибка передачи сохраняет локальную копию.
6. Добавить журнал результата, повтор передачи без дублирования и восстановление из внешней копии. Секреты/копии — вне Git; безопасность/шифрование задаются явно.

Готово, когда восстановление проверено в том числе при недоступности, частичной передаче и повреждении копии. Серверный режим самого SmartSQL для этого не требуется.

## 8. Диплом и выпуски

Дипломная проверка идёт через все этапы: студенты, организации, места/сроки практики, документы и статусы. После каждого большого этапа прогонять создание/открытие, импорт, фильтр, изменение, экспорт и восстановление на синтетических данных. Предметные сущности не встраиваются в ядро.

Первую удобную версию PostgreSQL/SQLite выпускать после A–D и русской приёмки, не ждать остальных СУБД/ИИ. Для дипломной демонстрации отдельно зафиксировать обязательные сценарии, отчёты и материалы защиты. При появлении дедлайна пересмотреть объём выпуска, сохранив проверки данных.

Поставка: воспроизводимая сборка, инструкция первого запуска, пример без реальных персональных данных, ограничения, проверка обновления/переноса файлов и восстановления. Основная текущая проверка — Windows; Linux/macOS требуют собственных сборок и приёмки до объявления поддержки.

## 9. Параллельная работа и завершение этапа

Сначала фиксируем контракт и владельцев файлов, затем делегируем независимые направления. Пример первого цикла: PostgreSQL-операции и проверки; обычный SQLite-обозреватель и проверки; UI и состояния команд. Основной агент интегрирует общие контракты, запускает сборку/тесты, ведёт документацию и Git. Зависимые изменения ждут фиксации общего контракта; агенты не редактируют один файл одновременно.

Модели: `gpt-6.1-sol` medium или `gpt-5.6-sol` high; без Astra и extra-high. Число задач определяется доступными слотами. Технологии и универсальные механизмы добавляются под текущий срез.

Этап закрывается, когда:

1. Сценарий работает, ограничения названы явно.
2. `scripts/Build.ps1` и необходимые `scripts/Test.ps1` проходят на D:. Запись проверяется только на отдельных синтетических базах; пропуск не считается успехом.
3. Затронутый UI проверен вручную или честно отмечено, что эта проверка остаётся до пользовательской приёмки.
