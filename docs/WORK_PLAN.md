## Текущий срез 16 октября 2026: первый инспектор T12

В обычных PostgreSQL/SQLite объектах панель «Структура» → «Подробнее…» открывает поля, собственные ограничения, индексы и доступные нативные определения. Секции явно показывают полноту; неизвестные свойства не подменяются догадками. PostgreSQL сохраняет PK/FK/UNIQUE/CHECK/exclusion, deferred/validated и expression/partial/INCLUDE/invalid indexes; SQLite показывает PRAGMA и исходный SQL с частичной структурированной интерпретацией. Входящие FK, domain constraints и граф зависимостей не входят в охват. Изменение структуры/прав/политики удаления не добавлено. Успешное чтение сохраняет страницу, фильтры и write handles. [Границы и проверка](NATIVE_INSPECTOR_PLAN.md), D050.

Debug: 0 предупреждений/ошибок; все **614 тестов** (Domain 1 / Application 129 / Infrastructure 445 / Desktop 39), включая **60 реальных PostgreSQL-фактов**, прошли без пропусков. Новые 21 проверки охватывают контракт/лимиты, quoted/compound keys, FK target permissions, deferred/NOT VALID/exclusion, expression/partial/INCLUDE, failed concurrent invalid index, view/materialized view, actual UPDATE после инспекции, UTF-16 и повреждённый UTF-8 SQLite, неизменность файлов, отмену/disposal. Субагенты подготовили провайдеры/UI и нашли дефект кодировки; после их usage limit основной агент завершил исправления, тесты и интеграцию. Полное независимое ревью не заявляется. Собственный PostgreSQL-кластер штатно остановлен.

Новая ручная приёмка не выполнена: computer-use не инициализируется (`failed to write kernel assets ... os error 3`). Независимый код T12 выполнен во время ограничения; T11 не объявлен принятым. ## 1. Финальная цель

Универсальный desktop-клиент для структурированных данных в направлении DBeaver: подключение к разным СУБД, изучение таблиц, работа с данными, запросы, обмен и перенос через единое понятное рабочее место.

Целевая версия включает:

- SQLite, PostgreSQL, MySQL/MariaDB и SQL Server с общими сценариями и явными различиями возможностей.
- Два полноценных режима: работа с таблицами для пользователей Excel и расширенная работа с SQL/структурой.
- CSV/JSON/XLSX, перенос между провайдерами и безопасные изменения структуры с отчётом о несовместимости до записи.
- Локальные и внешние резервные копии с проверенным восстановлением; облачные диски и личные серверы как дополнительные места хранения.
- Локального помощника через Action/Permission, подтверждения и аудит; без произвольного SQL-доступа модели.
- Дипломный сценарий педагогической практики на универсальном ядре, пригодном для других предметных областей.

Полезные версии выпускаются до завершения всех пунктов. ИИ и остальные СУБД не являются условием первой удобной версии PostgreSQL/SQLite. Требования Google/Яндекс backup/restore уточнены аудитом; отдельные локальные preview не объявляются завершённой облачной версией.

## 2. Подтверждённые приоритеты

1. Ближайший большой результат — удобная и стабильная работа с PostgreSQL и SQLite.
2. Оба режима важны: выбор при первом запуске, запоминание выбора, постоянная кнопка переключения.
3. Для нескольких баз реализовано одно основное `WorkspaceWindow` с общим деревом и вкладками. Следующий шаг — ручная визуальная приёмка и развитие нативных операций внутри этой оболочки.
4. Сначала полноценный русский интерфейс, затем полный английский перевод.
5. Внешний вид доводим по двум присланным референсам вместе с функциями: тёплая светлая тема, зелёный акцент, аккуратные таблицы и единые диалоги.
6. Календарного дедлайна нет. Работа делится на небольшие проверяемые этапы; даты выпуска появятся после оценки конкретного объёма.
7. Всё создаваемое проектом — на D:. Локальные данные, копии, веса и результаты тестов — вне Git; проверенные этапы коммитятся.
8. Облачные диски и личные серверы для копий — последующий этап после устойчивой работы с внешними базами.

B развивается вместе с A; доводка UI продолжается на C–F. Изучение PK/FK для N1/N2 предшествует полному инспектору C. Совместимость проверяется уже в D и каждом новом провайдере. Безопасная смена типов локального проекта может стать отдельным небольшим шагом до полной межпровайдерной миграции.

После фильтров и обмена отдельно добавить быстрые расчёты (количество, сумма, среднее) и простые графики по поддерживаемым типам. Проверять область расчёта — текущий результат или вся таблица — и точность чисел. Форматирование SQL, планы выполнения и дополнительные редакторы значений развивать небольшими расширениями C; инструменты появляются в интерфейсе после реализации.

Ручной SQL — самостоятельная функция опытного пользователя. Проверка первого слова SELECT недостаточна: режим чтения и права задаёт провайдер. Пользовательские функции не объявляются полной песочницей внешних побочных эффектов. Произвольная SQL-запись, длительные ручные транзакции и общая отмена внешних операций требуют отдельного решения и проверок.

## 6. Текущий интерфейс и его расширение

Ориентир — дерево подключений/объектов в [DBeaver](https://dbeaver.com/docs/dbeaver/Database-Navigator/) и дерево слева с вкладками рабочего места в [pgAdmin](https://www.pgadmin.org/docs/pgadmin4/latest/user_interface.html). Базовая схема уже реализована в `WorkspaceWindow`; инспектор и будущие типы вкладок добавляются небольшими срезами.

```text
Верх: открыть / подключить / импорт / действия активной вкладки / переключить режим
Слева: подключения → базы/схемы → таблицы/представления
Центр: вкладки таблиц и SQL; основная площадь — данные и результаты
Справа: сворачиваемые структура / свойства / ограничения объекта
Снизу: активное подключение, чтение/запись, результат и состояние загрузки
```

В простом режиме — таблицы, поиск, фильтры, записи и понятный импорт. В расширенном — те же данные плюс SQL, подробная структура, история и готовые дополнительные инструменты. Переключение меняет детализацию, а не подключение и не разрешение записи.

Группы команд: подключения, данные, запросы, импорт/экспорт, структура, копии/восстановление, настройки. У действия — единая подпись, обработчик, доступность и горячая клавиша, если нужна. Общие стили/иконки/ресурсы отделены от бизнес-операций. Кнопки будущих функций появляются вместе с рабочими сценариями.

После каждого нового сценария проверяются размеры/отступы/шрифты, таблицы, пустые/ошибочные/загружаемые состояния, фокус и читаемость. Приёмка включает обычное/минимальное окно, масштаб 100/150/200%, длинные названия и путь с клавиатуры. Иконки-кнопки, таблицы и вкладки имеют доступные имена/роли; ошибки, NULL и запрет записи обозначаются текстом, а не только цветом. Проверяются контраст, возврат фокуса после диалогов и короткий сценарий с экранным диктором Windows. Пользователь разрешил управление SmartSQL для таких тестов на синтетических данных D:; minimum size, High DPI и Narrator в текущем срезе ещё не проверены.

15 октября пользователь отдельно попросил сохранить текущий порядок и впоследствии проверить/доделать **весь UI**: сейчас не всё выровнено и не везде плавные переходы. В T23 обязателен отдельный полный проход по всем представлениям, согласование сетки/плотности/высот/отступов и переходов вкладок/режимов/панелей/загрузки без мерцания, скачков и потери состояния. Скриншот фиксирует в том числе обрезание заголовков инспектора. Это незакрытая приёмка, не основание преждевременно менять функциональный порядок.

Английский вводится после полного извлечения русских строк диалогов, статусов, валидации и провайдерных диагностик. Нужны совпадение ключей RU/EN, отсутствие смешения языков, корректное форматирование без изменения значений. Для первого перевода допустимо применять язык при следующем запуске.

Модель развивается отдельно в [DimaFi/SmartSQL-ML](https://github.com/DimaFi/SmartSQL-ML). Единственное рабочее место для всего ML — `D:\Code\SmartSQL-model`; внутри него остаются source, docs/scripts, datasets/профили, веса, эксперименты, кэши и временные/test/benchmark результаты. Самостоятельные скрипты сборки/тестов и изоляция пакетов подготовлены; 9 существующих тестов используют stub-ответы. Это не интеграция реальной модели или обучение. Главный приоритет PostgreSQL/SQLite и граница Action/Permission сохраняются.

## 7. Облачные копии и восстановление: уточнённые требования

16 октября пользователь выбрал Google Диск и Яндекс Диск первыми, автоматическое копирование/восстановление — основным облачным сценарием. Постоянная кнопка облака/статус должны давать быстрый доступ. Mail и универсальные назначения следуют после этих двух. Ранее общий пункт был отложен; теперь подтверждён конкретный объём, аудит/предлагаемый цикл описаны в [USER_ENTRY_AND_CLOUD_AUDIT.md](USER_ENTRY_AND_CLOUD_AUDIT.md). Реализация ещё не выполнена.

1. Разделить commit на локальном файле/сервере, проверенный snapshot, доставку в облако и проверенное восстановление. Возраст/scope/аккаунт/ошибки видны отдельно для каждого назначения. Запись в sync folder не означает cloud verified.
2. Сначала общий согласованный snapshot/restore и durable queue: SQLite Online Backup API, проверка/атомарный publish; PostgreSQL dump/restore — отдельный provider-specific срез, не CSV и не произвольное копирование server directory.
3. Google: официальный desktop OAuth/минимальные права/видимая папка; Яндекс: официальный REST/OAuth и ограниченная папка. Проверить реальные регистрации/доступ/загрузку/скачивание и восстановление каждого сервиса на synthetic D:-данных перед заявлением готовности. Личные аккаунты в аудите не подключались.
4. Автоматический режим при запущенном приложении: выбранное расписание/изменения, ограничения частоты/места, retry и очередь после перезапуска. Фоновая работа при закрытом приложении требует отдельного явно включаемого механизма и не обещается.
5. Новые версии не затирают предыдущие; при ошибках остаются локальный снимок/очередь/последняя проверенная копия. Проверки quota/revoked token/обрыва/потерянного ответа/hash mismatch/двух устройств обязательны. Политики шифрования, ключей и retention фиксируются отдельными решениями без собственной криптографии.
6. Restore сначала в новый файл/БД с проверкой; замена активного источника отдельно подтверждается и защищена копией. Восстановление после потери ПК/переустановки и переносимость ключей — обязательная приёмка, не только upload success.
7. Общий PostgreSQL на существующем подходящем ПК/сервере — доступный путь одновременной работы. Для варианта без сервера описать лишь поочерёдную передачу согласованных snapshots; общая живая SQLite в облачной папке и автоматический merge не предлагаются.

Данные разработки/тестов остаются на D:. Отдельную product storage policy для ПК без D:, устойчивых данных вне versioned EXE и совместимого обновления нужно реализовать до широкого распространения. Эти требования не означают установку SmartSQL application server или внедрение ИИ.

## 8. Диплом и выпуски

Дипломная проверка идёт через все этапы: студенты, организации, места/сроки практики, документы и статусы. После каждого большого этапа прогонять создание/открытие, импорт, фильтр, изменение, экспорт и восстановление на синтетических данных. Предметные сущности не встраиваются в ядро.

Первую удобную версию PostgreSQL/SQLite выпускать после A–D и русской приёмки, не ждать остальных СУБД/ИИ. Для дипломной демонстрации отдельно зафиксировать обязательные сценарии, отчёты и материалы защиты. При появлении дедлайна пересмотреть объём выпуска, сохранив проверки данных.

По просьбе пользователя поставка формируется уже сейчас: [Publish/Run-Published](DELIVERY.md), self-contained EXE/ZIP и manifest/SHA в соседнем `D:\Code\SmartSQL-builds`, версии не перезаписываются; [иконки](BRANDING.md) входят в приложение. Реальная автономная Windows x64 сборка запущена и частично проверена. Inno Setup-сценарий подготовлен, ISCC отсутствует: installer/обновление/удаление ещё не приняты. Продолжение: установка/обновление с сохранением данных, инструкция первого запуска, синтетический пример и восстановление. Linux/macOS требуют собственных сборок и приёмки до объявления поддержки.

## 9. Параллельная работа и завершение этапа

Сначала фиксируем контракт и владельцев файлов, затем делегируем независимые направления. Пример первого цикла: PostgreSQL-операции и проверки; обычный SQLite-обозреватель и проверки; UI и состояния команд. Основной агент интегрирует общие контракты, запускает сборку/тесты, ведёт документацию и Git. Зависимые изменения ждут фиксации общего контракта; агенты не редактируют один файл одновременно.

Модели: `gpt-6.1-sol` medium или `gpt-5.6-sol` high; без Astra и extra-high. Число задач определяется доступными слотами. Технологии и универсальные механизмы добавляются под текущий срез.

Этап закрывается, когда:

1. Сценарий работает, ограничения названы явно.
2. `scripts/Build.ps1` и необходимые `scripts/Test.ps1` проходят на D:. Запись проверяется только на отдельных синтетических базах; пропуск не считается успехом.
3. Затронутый UI проверен вручную или честно отмечено, что эта проверка остаётся до пользовательской приёмки.
4. Обновлены матрица, план и значимые архитектурные решения.
5. В Git попали только проверенные исходники/тесты/документация; данные, веса, копии и временные артефакты игнорируются.

Порядок пересматривается при новом дедлайне, обязательном сценарии, ограничении провайдера или существенном результате проверок. Календарные сроки сейчас не назначены.
