# Облачные копии SmartSQL: варианты и границы

Дата проверки официальных источников: **16 октября 2026**. Это исследование и предложение следующего среза, а не реализованная интеграция или принятое архитектурное решение. Личные аккаунты, токены и диски не подключались; сетевые операции с пользовательскими данными не выполнялись.

## Рекомендация для первого среза

Пользователь подтвердил первые два провайдера: **Google Drive и Яндекс Диск**. Основной согласованный сценарий — **автоматическое резервное копирование и восстановление**; одновременную работу предпочтительно организовать через сервер. Подготовить два независимых адаптера. Внутренний порядок проверки: ручные команды «Создать облачную копию», «Мои копии», «Восстановить в новый локальный файл», затем обязательный для целевого среза автоматический режим после проверки восстановления. Для Mail подтвердился официальный WebDAV: это реальный следующий кандидат, но публичная документированная REST API именно потребительского Облака Mail для стороннего desktop-клиента в этом аудите не подтверждена. Не использовать внутренние web endpoints, cookies/CSRF и обратную разработку логина.

Быстрый доступ означает сохранённое назначение и понятную последнюю проверенную копию. Он не требует открывать рабочую SQLite через облачный диск. В интерфейсе отдельно показывать:

| Состояние | Что подтверждено |
| --- | --- |
| Сохранено локально / на сервере | Транзакция текущего провайдера успешно завершена: SQLite в рабочем файле, PostgreSQL на сервере |
| Локальная копия проверена | Создан отдельный согласованный снимок, прошедший проверки |
| Передано в папку синхронизации | Файл записан локально; получение облаком пока не подтверждено |
| Облачная копия проверена | Удалённые байты/контрольная сумма сопоставлены с готовым артефактом |
| Восстановление проверено | Конкретная копия загружена и прошла проверку восстановления |

Облачная ошибка не отменяет уже выполненное локальное сохранение. Облачная копия не предоставляет совместную транзакционную работу: два устройства создают самостоятельные версии; автоматического слияния баз нет.

## Подтверждённые возможности провайдеров

### Google Drive

Для desktop требуется зарегистрированный OAuth client установленного приложения, системный браузер и корректный callback; применять PKCE S256 и проверку `state`, не встроенный сбор пароля. Desktop-приложение не может хранить client secret как секрет. Refresh token нужен для доступа без нового входа, но может перестать работать; отключение аккаунта и повторная авторизация должны быть штатными сценариями. См. [официальный installed-app OAuth](https://developers.google.com/identity/protocols/oauth2/native-app).

Предпочтение: **обычная видимая папка SmartSQL, созданная приложением, со scope `drive.file`**. Этот scope даёт доступ к созданным приложением или явно открытым/переданным ему файлам, не всему диску. Произвольная существующая папка требует корректного механизма предоставления доступа; строка пути сама по себе его не даёт. Полный `drive`/`drive.readonly` для этого среза не нужен. Публикация OAuth-приложения требует настройки consent и применимых проверок; нельзя обещать публичную готовность только после получения тестового client ID. [Scopes и verification](https://developers.google.com/workspace/drive/api/guides/api-specific-auth).

`appDataFolder` со scope `drive.appdata` скрыт от пользователя и других приложений; его удаляют при удалении приложения из My Drive, пользователь также может удалить данные вручную. Он подходит для служебной конфигурации, но **не для единственного пользовательского backup-хранилища**. Это отличается от обычной видимой папки. [Официальные ограничения app data](https://developers.google.com/workspace/drive/api/guides/appdata).

Для бинарных снимков использовать `uploadType=resumable`: хранить идентификатор сессии безопасно, запрашивать фактически принятый диапазон после обрыва; не выводить успех по числу отправленных байтов. Документация указывает срок жизни сессии около недели; истечение требует новой сессии. Не преобразовывать `.db`/архив в Google Docs/Sheets. [Resumable upload и ошибки](https://developers.google.com/workspace/drive/api/guides/manage-uploads).

Проверять `id`, размер и доступные `sha256Checksum`/`md5Checksum` через отдельное чтение метаданных; SHA-256 бывает недоступен, MD5 применим к бинарным файлам. Отсутствующее поле не означает совпадение: строгая проверка тогда скачивает объект и считает локальный SHA-256. Не использовать имя или `modifiedTime` как идентичность содержимого. [Files resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/files).

Новые backup-версии лучше хранить отдельными неизменяемыми файлами. Drive может удалять старые бинарные revisions: `keepForever` ограничен 200 версиями и расходует квоту. История revisions не заменяет собственную политику хранения и не даёт бессрочной сохранности. [Правила revisions](https://developers.google.com/workspace/drive/api/guides/manage-revisions).

### Яндекс Диск

Официальный REST API работает через `cloud-api.yandex.net/v1/disk`; пользовательский доступ авторизуется OAuth. Минимальный кандидат — `cloud_api:disk.app_folder`, без `disk.read`/`disk.write` на весь диск. Полные права запрашивать только если появится отдельно согласованный сценарий произвольных папок. Регистрация приложения и точный desktop OAuth flow должны быть проверены отдельно перед реализацией; debug token из документации не является производственным UX. [Доступ, scopes и регистрация](https://yandex.com/dev/disk-api/doc/en/concepts/quickstart).

Namespace папки приложения (`app:/`) требует отдельной проверки list/upload/download/delete именно с ограниченным токеном. Не выводить работоспособность app-folder из успешного запроса к `disk:/`. Страница «Папки приложений» была связана из официального quickstart, но её тело в используемом web-инструменте недоступно; это остаётся пунктом проверки, а не доказанной приёмкой.

Документированная загрузка: получить upload URL через `GET /resources/upload`, затем отправить байты `PUT` по полученному адресу. Всегда задавать `overwrite=false`; upload URL чувствителен, OAuth на сам uploader не передаётся. URL ограничен по времени. `202 Accepted` означает, что файл ещё не перемещён в Диск; нужна последующая проверка готовности и содержимого. `507` — нехватка места, `413` — превышение допустимого размера. Размер зависит от условий сервиса; не закреплять тарифные числа в контракте приложения. [Официальный upload protocol](https://yandex.com/dev/disk/api/reference/upload.html).

Официальная модель SDK содержит `size` и `md5`; upload-реализация Яндекса также использует SHA-256 и диапазоны для восстановления передачи. Однако наличие SHA-256 в upload-протоколе не доказывает гарантированное наличие `sha256` во всех metadata-ответах. На первом этапе проверять доступные remote hash/size и выполнять обратное скачивание для SHA-256, если сильная серверная сумма не подтверждена. Не обещать resumable parity с Google до отдельной проверки текущего сервиса. [Модель ресурса Яндекса](https://github.com/yandex-disk/yandex-disk-restapi-java/blob/master/disk-restapi-sdk/src/main/java/com/yandex/disk/rest/json/Resource.java), [официальный upload/resume source](https://github.com/yandex-disk/yandex-disk-restapi-java/blob/master/disk-restapi-sdk/src/main/java/com/yandex/disk/rest/RestClientIO.java). SDK — исторический первичный источник, не подтверждение текущего SLA.

API публикации существует, но **publish не является финализацией backup-upload**: он меняет доступ к ресурсу. Не вызывать его автоматически, не создавать публичных ссылок для копий. Возможность «поделиться» — отдельное будущее действие с подтверждённой аудиторией. [Официальная публикация](https://yandex.ru/dev/disk/api/reference/publish.html).

### Облако Mail

Официально подтверждён HTTPS WebDAV endpoint `https://webdav.cloud.mail.ru`. Нужен **пароль внешнего приложения**, обычный пароль аккаунта не подходит. Инструкция обновлена 03.03.2026; отдельно предупреждает о недостоверном прогрессе больших загрузок через Windows WebDAV и советует отключать LOCK для davfs2. Поэтому сетевой диск/индикатор копирования нельзя считать доказательством готовности; протокол и обратная проверка должны быть реализованы явно. SmartSQL не должен менять службы Windows или глобальные настройки davfs2. [Официальная инструкция](https://help.mail.ru/cloud/desktop/webdav/).

Эта инструкция сейчас не устанавливает требование платного тарифа для самого WebDAV; обещать его бесплатность для любого аккаунта также нельзя. Отдельная страница desktop-клиента говорит о бесплатной загрузке в само Облако Mail и лимите 10 файлов в сутки в другие облака через **их desktop-клиент**. Это не подтверждённый лимит прямого WebDAV SmartSQL. [Условия desktop-тарифа, 18.03.2026](https://help.mail.ru/cloud/desktop/rates/).

Численный WebDAV max-file-size и provider checksum/resume гарантии по актуальным официальным источникам здесь не установлены: нужны проверка конкретного аккаунта/тарифа и ограниченные synthetic upload/download тесты. При переполненном едином пространстве Почты и Облака сервис ограничивает доступ/загрузку; длительное переполнение может привести к удалению. Нельзя считать облачную копию бессрочной. [Официальные последствия переполнения](https://help.mail.ru/cloud/files/overflowing/).

Статус: **WebDAV-кандидат после проверки совместимости; отдельный native REST-адаптер не подтверждён**. Авторизация Mail для других сервисов и API Постмастера не доказывает наличие API файлов Облака. Не использовать сторонние reverse-engineered библиотеки как основание обещания поддержки.

### Переносимые варианты и другие сервисы

| Вариант | Предложенный статус | Ограничение |
| --- | --- | --- |
| Выбранная локальная папка клиента синхронизации | Первый переносимый fallback | Только готовые снимки; без remote API статус «передано локальному клиенту», без облачной гарантии |
| HTTPS WebDAV | Отдельный адаптер после проверки каждого сервиса | ETag непрозрачен и не обязан быть hash; LOCK/MOVE/условная запись/квоты отличаются |
| Nextcloud WebDAV | Проверяемый будущий кандидат | Официально описаны file operations, нужна совместимость конкретного сервера/версии |
| OneDrive Microsoft Graph | Будущий отдельный адаптер | Есть upload sessions; OAuth, scopes, conflicts/verification проверяются отдельно |
| Другие хранилища/S3-compatible | Пока не заявлять поддержку | Совместимость протокола не подтверждает конкретные guarantees и restore |

[Стандарт WebDAV RFC 4918](https://www.rfc-editor.org/info/rfc4918/), [официальный Nextcloud WebDAV](https://docs.nextcloud.com/server/latest/developer_manual/client_apis/WebDAV/basic.html), [официальные OneDrive upload sessions](https://learn.microsoft.com/en-us/graph/api/driveitem-createuploadsession?view=graph-rest-1.0).

## Предлагаемый безопасный путь данных

1. **Подготовить согласованный снимок локально.** Для SQLite использовать Online Backup API в новый собственный файл, а не File.Copy открытого `.db` отдельно от WAL/SHM. Проверить завершение API, `quick_check`/целостность, ожидаемую схему/версию и возможность открытия без sidecars. Рабочую базу не размещать в sync/WebDAV-папке. Для incremental backup задать отмену и общий бюджет: при постоянных изменениях копирование может перезапускаться. [SQLite Online Backup](https://www.sqlite.org/backup.html), [ограничения сетевых файлов SQLite](https://www.sqlite.org/useovernet.html).
2. **Для PostgreSQL сформировать настоящий backup-артефакт.** Предпочтителен совместимый `pg_dump -Fc` с проверкой exit code/ошибок и тестовым `pg_restore` в отдельную БД. Экспорт таблицы CSV/JSON/XLSX не сохраняет полную схему/ограничения/объекты и backup базы не заменяет. `pg_dump` охватывает одну БД; роли/tablespaces и прочие глобальные объекты требуют отдельной политики. Для production PITR/физические копии находятся за границей первого desktop-среза. [Официальный pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html).
3. **Зафиксировать артефакт до сети.** Сгенерировать snapshot UUID, UTC, тип провайдера/формат, размер, SHA-256 и versioned manifest. Не включать пароли, SQL history, профили с секретами, локальные пути или весь каталог runtime. Закрыть/flush файлы, опубликовать локально без перезаписи. В текущем workspace все snapshots/outbox/download/temp/результаты — на D:, отдельно от исходной БД и её sidecars; пути не следуют reparse/symlink за разрешённую границу. Путь production-профиля должен быть явным переносимым решением, а не жёстко зашитым `D:\Code`.
4. **Загрузить неизменяемые байты.** Каждой попытке соответствует snapshot ID + хеш; новые версии не затирают старые. Хранить состояние durable outbox на D:, потоковая передача с лимитами памяти/размера, отменой и deadlines. Парольные capture не удерживать после отключения аккаунта.
5. **Проверить remote.** Получить точный ID/version объекта, размер и checksum; при отсутствии сильного checksum скачать и пересчитать SHA-256. Создать completion manifest только после проверки payload; если manifest отдельный, он сам не доказывает целостность payload. Повторно сверять на восстановлении. Статус unknown после сетевого обрыва разрешать через чтение точного ID/сессии/хеша, не через слепое создание/overwrite.
6. **Восстановить в новый локальный файл.** Сначала ограниченно скачать на D:, проверить manifest/schema версии, размер/хеш и шифрование; затем SQLite integrity/схему или PostgreSQL restore в отдельную БД. Только после этого предлагать открытие. Замена существующей базы — отдельное подтверждение и предварительная локальная копия, закрытие соединений и проверка sidecars. Автоматически SQL из чужого dump не выполнять: восстановление PostgreSQL может исполнять код из архива и требует доверенного источника/изолированной проверки.

Это предложение единого прикладного процесса; transport-адаптеры Infrastructure сообщают фактические capabilities: resume, remote hash, conditional create/version, list/download/delete. Application не содержит SQL/SDK конкретного облака. На первом этапе достаточно coordinator + snapshot producer + два небольших адаптера; распределённая синхронизация и сервер не требуются.

## Отказы, безопасность и хранение

- Retry только временных сетевых/429/5xx с ограниченным exponential backoff + jitter и учётом Retry-After. Ошибки авторизации, квоты, доступа, размера и hash mismatch различать; не зацикливать, не удалять последнюю рабочую копию. После прекращения загрузки сохранять проверенный локальный снимок и понятное «ожидает отправки».
- Отозванный token требует повторного входа; нельзя повышать scope или переключать аккаунт автоматически. Refresh/access tokens, app passwords и upload/download session URLs не писать в JSON-профили, журналы, Git или backup. Использовать защищённое платформенное хранилище/защищённый локальный secret store, явное отключение/удаление credential; не менять глобальные настройки ОС. В аудите никакие реальные credentials не запрашиваются.
- TLS проверяется штатно, без обхода сертификатов. Произвольные WebDAV endpoints требуют явного выбора пользователя; не пересылать Authorization при смене origin/redirect и не принимать remote пути как локальные. Метаданные/manifest/архивы недоверенные: bounded parsing, лимит скачивания/распаковки, запрет path traversal и zip bombs.
- Для чувствительных баз предложить клиентское authenticated encryption до upload, отдельно согласовать формат, KDF и переносимое восстановление ключа; не придумывать собственную криптографию. Ключ не хранить рядом в том же облаке. Потеря единственного ключа означает потерю восстановления. Проверять hash ciphertext при передаче и plaintext после расшифрования; без реализованного шифрования интерфейс честно сообщает, что облачный провайдер получает содержимое.
- Retention пользователь задаёт отдельно (например последние N + дневные/недельные), сначала без автоматического удаления. Удалять только принадлежащие SmartSQL версии после подтверждённой новой копии, сохранять последнюю проверенную и отмеченные пользователем. Два устройства создают отдельные UUID/device generations; при конфликте сохранять обе версии. Общего mutable `latest.db` и last-writer-wins быть не должно.
- Две независимые облачные цели уменьшают зависимость от одного аккаунта, но повышают расход квоты и объём раскрытия данных. Начальный выбор Google/Яндекс не означает автоматическую отправку в оба: пользователь явно подключает назначения. Локальная копия остаётся необходимой; cloud trash/revisions не заменяют backup retention.

## Автоматический режим и доступная совместная работа

Автоматическое копирование должно работать по выбранным пользователем правилам: интервал и/или накопленные локальные изменения, ограничение частоты и один активный snapshot/upload на проект. Запись каждой ячейки не должна синхронно ждать сеть. При офлайне остаётся durable outbox; после восстановления связи приложение отправляет готовые снимки и проверяет результат. Coalescing непросланных автоматических снимков допускается только по явной политике, без удаления последней проверенной копии и пользовательских ручных точек.

**В первом варианте автоматические задачи выполняются, пока SmartSQL запущен.** При закрытии отмена/дренирование сохраняют очередь; следующее открытие проверяет пропущенный срок и возобновляет отправку. Закрытое приложение само не просыпается и не создаёт новые копии. Постоянная служба или системный планировщик — отдельная явно включаемая функция с проверенным местом хранения credentials, журналом и поведением без входа пользователя; сейчас её не обещать и глобальные настройки не менять.

| Сценарий | Доступный путь | Граница надёжности |
| --- | --- | --- |
| Несколько людей работают одновременно | Одна PostgreSQL БД на уже имеющемся постоянно включённом компьютере/сервере организации, индивидуальные DB-роли и защищённый канал | Нет новой платы за аренду, если ресурс уже есть; владелец обеспечивает uptime, обновления и отдельный backup. Не открывать БД всему интернету |
| Совместная работа между площадками | Небольшой арендованный сервер или управляемый PostgreSQL после сравнения актуальных условий | Конкретного провайдера/цену здесь не выбираем; заранее учесть хранение, резервные копии, сеть, администрирование и восстановление |
| Нет сервера и одновременность не требуется | Один ответственный редактор; явная передача готового проверенного снимка другому человеку, восстановление в новый локальный файл | Только работа по очереди; организационный порядок передачи не распределённая блокировка. Две независимые ветки не сливаются автоматически |

Для shared PostgreSQL права каждого участника ограничиваются сервером; режим Simple/Advanced не заменяет DB permissions. Совместная работа не даёт AI unrestricted SQL. Backup сервера остаётся отдельной задачей владельца; desktop-копия может быть дополнительной защитой, но не единственной production-стратегией. Сетевой доступ через server engine соответствует [рекомендации SQLite для нескольких клиентов](https://www.sqlite.org/useovernet.html). Собственный облачный сервер SmartSQL или слой синхронизации SQLite для этого среза не требуется.

## Внедрение и проверка результата

1. Зафиксировать отдельное решение: Google/Яндекс и автоматические копии с восстановлением уже выбраны пользователем; уточнить видимость папки, типы БД, частоту/retention и требования к шифрованию. Не менять текущие права SQL/редактирования.
2. Сначала общий локальный snapshot/restore pipeline и симуляция транспорта с injected failures. Затем Google visible folder + `drive.file`, Яндекс app-folder; каждый отдельно проходит protocol acceptance с synthetic D:-данными и добровольно авторизованным тестовым аккаунтом. Никаких скрытых аккаунтов приложения.
3. Проверить SQLite live WAL, конкурентные записи, user_version/схему/UTF-16/BLOB/Int64; restore из одного готового файла без оригинального WAL. Проверить PostgreSQL PK/FK/indexes/sequences/types/данные и восстановление dump; несовместимость утилиты/сервера диагностируется, а не обходит backup CSV-экспортом.
4. Проверить обрыв до/во время/после upload, потерянный финальный ответ, истёкшую session URL, перезапуск SmartSQL, cancel/закрытие, quota full, revoked token, hash mismatch, удалённый remote объект, два устройства и одинаковые имена. Ни один сценарий не повреждает исходник/последнюю копию и не показывает ложный успех.
5. Проверить восстановление после переустановки приложения/на другом устройстве; Google app access recovery, выбор правильного аккаунта/папки, переносимость шифровального ключа. Для Mail отдельно подтвердить разрешённый WebDAV и ограничения конкретного тарифа; для local-sync показывать только реально известный уровень подтверждения.
6. Приёмка автоматического режима: выбранный срок/изменения запускают ограниченное число задач, офлайн-очередь переживает перезапуск, ошибки не создают бесконечные retry, после запуска выполняется catch-up. Закрытое приложение не объявляется работающим фоновым сервисом. Ручная приёмка: одно понятное действие, быстрый список проверенных копий, прогресс/отмена/повтор, видимые время/возраст/назначение последней копии; отсутствие токенов/секретов в логах и экспортируемых настройках. Затем отдельно проверяется ограниченная retention.

**Осталось неизвестным:** реальные OAuth регистрации/verification приложения, фактические ограничения целевых аккаунтов, app-folder recovery Яндекса, текущие гарантии Яндекс resume/remote SHA-256, Mail max-file-size/checksum/resume/условная запись, работоспособность конкретных WebDAV реализаций. Документ не является сетевой, нагрузочной или restore-приёмкой.
