# Аудит входа в SmartSQL: локальный проект, Excel/CSV и действующая БД

Дата статического аудита: 16 октября 2026. Проверены текущие desktop-пути и реализация хранения/импорта. Приложение не запускалось, ручная UI-приёмка в этот аудит не входит.

## Проверенные пользовательские сценарии

1. **Новичок после Excel.** Хочет выбрать книгу, увидеть листы и значения, проверить типы и получить локальную рабочую базу без знания СУБД.
2. **Опытный пользователь без установленной СУБД.** Хочет создать локальный проект и таблицы, понимая путь, формат, резервные копии и возможности переноса.
3. **Пользователь действующей БД.** Хочет открыть существующий PostgreSQL или SQLite без незаметной миграции, копирования либо изменения исходника.

## Что уже реализовано

- Главное окно явно предлагает PostgreSQL, обычный SQLite, открытие/создание проекта SmartSQL и демонстрацию (`src/SmartSQL.Desktop/Views/WorkspaceWindow.cs:132-147`). Обычный SQLite после выбора файла получает отдельный экран режима доступа; рекомендован режим только чтения, изменение требует отдельного checkbox, показаны полный путь и каталог копий (`src/SmartSQL.Desktop/Views/NativeSqliteOpenDialog.cs:45-69`, `src/SmartSQL.Desktop/Views/NativeSqliteOpenDialog.cs:98-123`). Это хороший фундамент для сценария «посмотреть действующую БД без переноса».
- Создание проекта отказывается использовать уже существующий файл (`src/SmartSQL.Desktop/Views/WorkspaceWindow.cs:659-674`; дублирующая команда редактора — `src/SmartSQL.Desktop/Views/MainWindow.axaml.cs:193-210`). Ручная копия также не перезаписывает существующий файл (`src/SmartSQL.Infrastructure/SqliteWorkspace.cs:103-115`).
- Восстановление идёт через временную БД, проверяет формат SmartSQL и перед заменой создаёт safety backup (`src/SmartSQL.Infrastructure/SqliteWorkspace.cs:117-171`). Перед удалением поля или таблицы также создаётся отдельная копия (`src/SmartSQL.Infrastructure/SqliteWorkspace.cs:520-542`, `src/SmartSQL.Infrastructure/SqliteWorkspace.cs:558-573`).
- CSV и XLSX в существующую таблицу проходят mapping и подтверждение preview (`src/SmartSQL.Desktop/Views/MainWindow.axaml.cs:590-634`, `src/SmartSQL.Desktop/Views/MainWindow.Spreadsheets.cs:13-45`). Пропущенные исходные столбцы и незаполненные поля требуют отдельного подтверждения (`src/SmartSQL.Desktop/Views/CsvMappingDialog.cs:161-197`). Массовая вставка выполняется одной SQLite-транзакцией (`src/SmartSQL.Infrastructure/SqliteWorkspace.cs:597-623`).
- CSV может создать новую таблицу; пользователь выбирает названия и один из четырёх managed-типов, а все строки проверяются до создания (`src/SmartSQL.Desktop/Views/CsvNewTableDialog.cs:63-101`, `src/SmartSQL.Application/CsvImportSource.cs:38-71`). Создание таблицы вместе со строками атомарно (`src/SmartSQL.Infrastructure/SqliteWorkspace.cs:213-277`).
- XLSX читается без выполнения формул; формулы, ошибки, время и неподдерживаемые связанные типы отклоняются явно (`src/SmartSQL.Infrastructure/XlsxWorkbookSource.cs:175-235`). Интерфейс сообщает, что выбран только один лист и исходная книга не меняется (`src/SmartSQL.Desktop/Views/XlsxSheetDialog.cs:57`).
- Экспорт CSV/XLSX публикуется через временный файл и никогда не перезаписывает существующий результат (`src/SmartSQL.Infrastructure/AtomicFileExport.cs:3-36`). CSV для Excel обезвреживает начала формул (`src/SmartSQL.Application/CsvTransfer.cs:84-98`).

## Конкретные пробелы

### P1. До выбора задачи уже создаётся локальный проект

**Текущее поведение.** Конструктор оболочки сразу создаёт `MainWindow()` (`src/SmartSQL.Desktop/Views/WorkspaceWindow.cs:211-214`), а тот открывает `WorkspacePaths.DefaultDatabasePath` (`src/SmartSQL.Desktop/Views/MainWindow.axaml.cs:44-66`). `SqliteWorkspace` открывает путь в режиме создания и при отсутствии managed-схемы создаёт служебные таблицы (`src/SmartSQL.Infrastructure/SqliteWorkspace.cs:21-26`, `src/SmartSQL.Infrastructure/SqliteWorkspace.cs:44-100`). Первый диалог спрашивает только Simple/Advanced, а не исходную задачу (`src/SmartSQL.Desktop/Views/WorkspaceWindow.cs:241-255`).

**Последствие.** Новичок ещё не выбрал «Excel», «новый проект» или «существующая БД», но на диске уже появился проект. Пустая вкладка выглядит как осознанно открытая база, хотя пользователь её не создавал и не выбирал место хранения.

**Критерий исправления.** Первый полезный экран предлагает три понятных действия: «Импортировать Excel/CSV в новый локальный проект», «Создать пустой локальный проект», «Открыть существующую БД/проект». До явного выбора или открытия демонстрации пользовательский файл не создаётся. После выбора показываются назначение и полный путь.

### P0. Ошибочно выбранный пустой SQLite-файл может стать проектом SmartSQL

**Текущее поведение.** И проект SmartSQL, и обычный SQLite выбираются как `.db`: проект через «Открыть проект», обычная база через «SQLite…» (`src/SmartSQL.Desktop/Views/WorkspaceWindow.cs:133-145`, `src/SmartSQL.Desktop/Views/WorkspaceWindow.cs:639-655`). `SqliteWorkspace` отклоняет обычный файл только если нашёл пользовательские таблицы без `smartsql_tables`; пустой SQLite или файл без пользовательских таблиц проходит дальше и получает managed-схему (`src/SmartSQL.Infrastructure/SqliteWorkspace.cs:44-100`).

**Последствие.** Пользователь может перепутать два одинаково выглядящих `.db`. Непустая обычная база защищена отказом, но пустая действующая база изменяется без отдельного решения о миграции. Это нарушает ожидаемое правило «открыть существующую БД без преобразования».

**Критерий исправления.** «Открыть проект SmartSQL» принимает только файл с подтверждённой managed-сигнатурой/версией. Любой неизвестный SQLite, включая пустой, остаётся byte-for-byte неизменным и предлагается к открытию через обычный SQLite. Создание managed-схемы допускается только для нового пути, выбранного командой создания. Перед автоматическим upgrade существующего проекта показываются версия, путь и местоположение созданной копии.

### P1. Нет прямого пути «Excel → новый локальный проект/таблица»

**Текущее поведение.** XLSX-команда требует уже открытый проект и выбранную таблицу (`src/SmartSQL.Desktop/Views/MainWindow.Spreadsheets.cs:13-16`); её кнопка выключена без таблицы (`src/SmartSQL.Desktop/Views/MainWindow.axaml.cs:455-464`). Новую таблицу можно создать из CSV (`src/SmartSQL.Desktop/Views/MainWindow.axaml:139-151`, `src/SmartSQL.Desktop/Views/MainWindow.axaml.cs:317-357`), но аналога для XLSX нет. Для Excel остаются ручное создание полей, затем mapping, либо вставка из буфера.

**Последствие.** Самый вероятный новичковый сценарий начинается с проектирования схемы до просмотра книги. Пользователь должен заранее понять различие проекта, таблицы, поля и типов, хотя эти данные уже частично присутствуют в XLSX.

**Критерий исправления.** Отдельный мастер «Новый проект из Excel/CSV»: выбор исходника без изменения; выбор листа/диапазона и наличия заголовка; место нового проекта; имена таблицы и полей; тип каждого столбца с безопасным default `Текст`; preview фактически сохраняемых значений; итоговое подтверждение. Несколько листов не объединяются и не отбрасываются молча.

### P1. Preview показывает исходные примеры, а не итог после нормализации

**Текущее поведение.** Для новой CSV-таблицы показывается только первая исходная строка рядом с типом (`src/SmartSQL.Desktop/Views/CsvNewTableDialog.cs:120-146`), после проверки диалог возвращает preview и вызывающий код сразу делает commit (`src/SmartSQL.Desktop/Views/CsvNewTableDialog.cs:150-162`, `src/SmartSQL.Desktop/Views/MainWindow.axaml.cs:343-357`). Для существующей таблицы финальный grid также строится из `SampleRows`, то есть исходных строк, а не нормализованных `_rows` (`src/SmartSQL.Desktop/Views/CsvPreviewDialog.cs:23-35`, `src/SmartSQL.Application/CsvImportPreview.cs:11-29`). Фактическая запись повторно нормализует значения (`src/SmartSQL.Infrastructure/SqliteWorkspace.cs:616-623`).

**Последствие.** Пользователь подтверждает одно отображение, а сохраняется другое: `01.02.2026` становится `2026-02-01`, `Да` — `1`, числовая запись меняет каноническое представление. Ошибка формата будет найдена до commit, но допустимое преобразование не видно.

**Критерий исправления.** Preview показывает минимум пары «исходное → будет сохранено» для каждого преобразованного столбца, количество NULL/ошибок/изменённых значений и итоговые типы. Подтверждение новой таблицы отделено от настройки полей так же явно, как импорт в существующую.

### P1. NULL, пустая строка и пробельный текст неразличимы в managed-импорте

**Текущее поведение.** Общая нормализация превращает `null`, пустую и любую пробельную строку в `null` до проверки типа (`src/SmartSQL.Application/FieldValue.cs:8-15`). CSV parser возвращает одинаковую пустую строку для пустого поля и `""`; экспорт также записывает NULL как пустой текст (`src/SmartSQL.Application/CsvTransfer.cs:84-98`, `src/SmartSQL.Application/CsvTransfer.cs:100-160`). XLSX отклоняет пробельный текст, чтобы не изменить его тихо, но пустые ячейки проходят как пустота (`src/SmartSQL.Infrastructure/XlsxWorkbookSource.cs:221-238`).

**Последствие.** Для кодов, пометок и интеграций пользователь не может сохранить различие `NULL` / `""` / `"   "` в managed-проекте и не видит это как отдельное решение импорта. CSV round-trip этого различия не обеспечивает.

**Критерий исправления.** В мастере явно описана модель пустоты каждого формата. Если managed-модель пока хранит только NULL, preview считает и показывает все схлопываемые значения и требует подтверждения. Для будущего lossless-режима нужны отдельный NULL-маркер/формат и симметричный экспорт; нельзя угадывать NULL по пустой строке.

### P1. Ведущие нули и Excel-форматы требуют явного решения по столбцу

**Текущее поведение.** Новая CSV-таблица безопасно начинает со всех полей типа `Текст` (`src/SmartSQL.Desktop/Views/CsvNewTableDialog.cs:126-146`), поэтому текст `00123` сохраняется, пока пользователь сам не выбрал `Число`. Числовая нормализация канонизирует запись (`src/SmartSQL.Application/FieldValue.cs:18-22`, `src/SmartSQL.Application/FieldValue.cs:44-55`). XLSX читает хранимое число, а не внешний вид; формат `00000`, проценты и денежное оформление не переносятся, о чём создаётся общее предупреждение (`src/SmartSQL.Infrastructure/XlsxWorkbookSource.cs:144-149`, `src/SmartSQL.Infrastructure/XlsxWorkbookSource.cs:221-230`).

**Последствие.** Индексы, артикулы и почтовые коды могут потерять ведущие нули, если Excel уже хранит их числом либо пользователь выберет числовой тип. Общее предупреждение не указывает конкретные столбцы и примеры.

**Критерий исправления.** Тип по умолчанию остаётся `Текст`. Мастер отмечает столбцы с leading zeros, длинными числовыми идентификаторами и display-format; показывает конкретные raw/stored/display примеры. Выбор `Число` для такого столбца требует видимого подтверждения преобразования. Уже округлённые Excel значения нельзя обещать восстановить.

### P1. Импорт в существующую таблицу — только append без batch-undo или копии

**Текущее поведение.** Preview честно говорит, что строки будут добавлены (`src/SmartSQL.Desktop/Views/CsvPreviewDialog.cs:49-55`), а commit атомарно вставляет весь batch (`src/SmartSQL.Infrastructure/SqliteWorkspace.cs:597-623`). Но перед CSV/XLSX/clipboard import не создаётся safety backup и импортированный batch не получает handle для общей отмены (`src/SmartSQL.Desktop/Views/MainWindow.axaml.cs:630-634`, `src/SmartSQL.Desktop/Views/MainWindow.Spreadsheets.cs:39-43`, `src/SmartSQL.Desktop/Views/MainWindow.Spreadsheets.cs:93-98`). Проверки дублей/ключа импорта также нет.

**Последствие.** Технический сбой не оставит половину batch, но успешный ошибочный импорт на 100 000 строк трудно отменить; повторный запуск создаёт дубликаты.

**Критерий исправления.** Перед подтверждением явно указать режим `Добавить`, текущий/новый размер и политику дублей. После commit должен существовать безопасный способ отменить ровно этот batch либо автоматически созданная именованная копия и простой restore. Replace/upsert нельзя включать без отдельного preview и ключа сопоставления.

### P1. CSV покрывает узкий набор файлов Excel-экосистемы

**Текущее поведение.** Desktop читает CSV как строгий UTF-8, не предлагает кодировку (`src/SmartSQL.Desktop/Views/MainWindow.axaml.cs:334-342`, `src/SmartSQL.Desktop/Views/MainWindow.axaml.cs:607-617`). Parser принимает только `;` и `,`, всегда считает первую строку заголовками и ограничивает один импорт 100 000 строками (`src/SmartSQL.Application/CsvTransfer.cs:26-62`).

**Последствие.** CSV из старого Excel в Windows-1251, TSV и файл без заголовков отклоняются либо дают непонятный для новичка результат. Автоопределение разделителя не решает кодировку и структуру заголовка.

**Критерий исправления.** До commit показывать определённую кодировку/разделитель/заголовок; позволять вручную выбрать поддерживаемую кодировку и TSV. Ошибочная декодировка не заменяет символы. Режим «без заголовка» генерирует видимые имена полей, которые пользователь подтверждает.

### P2. Локальный проект не объяснён как отдельный формат, а не «обычная SQLite-схема»

**Текущее поведение.** Managed-проект хранит свои таблицы метаданных и физические пользовательские значения как `TEXT`, поверх четырёх прикладных типов (`src/SmartSQL.Infrastructure/SqliteWorkspace.cs:58-100`, `src/SmartSQL.Infrastructure/SqliteWorkspace.cs:207-277`). Обычный SQLite открывается другим provider-путём. В toolbar используются близкие слова «SQLite», «Открыть проект» и «Новый проект» без стартового сравнения (`src/SmartSQL.Desktop/Views/WorkspaceWindow.cs:132-147`).

**Последствие.** Опытный пользователь без сервера может ожидать обычную переносимую SQLite-схему, а получить внутренний формат SmartSQL. Новичок может считать «проект» папкой или копией Excel. Последующий перенос во внешнюю БД пока не является частью onboarding.

**Критерий исправления.** До создания кратко показать: проект SmartSQL — локальный managed-файл с удобными таблицами/типами; обычный SQLite — существующая нативная схема; PostgreSQL — подключение к уже работающему серверу. Не устанавливать сервер и не переносить данные автоматически. У проекта должны быть видимые пути экспорта и ограничения совместимости.

### P2. Путь данных зависит от способа и каталога запуска

**Текущее поведение.** Без `SMARTSQL_DATA_DIRECTORY` данные размещаются в найденном source workspace либо рядом с текущим executable в `data/local`; там же создаются temp и default DB (`src/SmartSQL.Desktop/WorkspacePaths.cs:6-30`, `src/SmartSQL.Desktop/WorkspacePaths.cs:33-60`). Для versioned portable-папок прямой запуск каждой версии может выглядеть как новая пустая установка. Native SQLite edit-копии вычисляются от того же каталога (`src/SmartSQL.Desktop/Views/WorkspaceWindow.cs:320-344`).

**Последствие.** Пользователь не понимает, где проект/настройки/история, а новая версия EXE может не увидеть прежний default. В текущей dev-политике копии требуют D:, что нельзя переносить как product-требование на ПК без D:.

**Критерий исправления.** Отдельно утвердить product storage policy: стабильный пользовательский каталог, независимый от версии EXE; portable-режим только явный; выбранный каталог показывается и может быть открыт/изменён; перенос выполняется как проверенная copy/move с подтверждением. Требование D: остаётся правилом текущей разработки и тестов, но поставка должна выбирать доступный отдельный каталог копий без ослабления правила «backup до write».

### P2. Безопасный отказ от overwrite выглядит как ошибка после Save As

**Текущее поведение.** Проект, backup и атомарный экспорт не перезаписывают файл (`src/SmartSQL.Desktop/Views/WorkspaceWindow.cs:665-673`, `src/SmartSQL.Infrastructure/SqliteWorkspace.cs:103-115`, `src/SmartSQL.Infrastructure/AtomicFileExport.cs:14-35`). Если системный Save dialog вернул существующий путь, пользователь получает ошибку и должен повторить выбор.

**Последствие.** Данные защищены, но привычное ожидание Save As не совпадает с результатом; для копий быстро появляются трудно различимые имена.

**Критерий исправления.** После конфликта предложить безопасные варианты: выбрать другое имя, автоматически добавить timestamp/version или отменить. Перезапись допускается только как отдельное явное действие с атомарной заменой и восстановимой предыдущей версией; обычный export/backup остаётся create-new.

### P2. Нет единого списка недавних проектов, источников и копий

**Текущее поведение.** Shell хранит mode/theme и несекретные PostgreSQL-профили, но стартовый путь состоит из toolbar и автоматически открытого default project (`src/SmartSQL.Desktop/Views/WorkspaceWindow.cs:241-304`). Полный путь текущего managed-файла отображается внутри редактора (`src/SmartSQL.Desktop/Views/MainWindow.axaml.cs:85-88`), native SQLite показывает путь и backup directory (`src/SmartSQL.Desktop/Views/NativeSqliteOpenDialog.cs:64-69`), но общего «Недавние / Копии / Где мои данные» нет.

**Последствие.** После первого успешного импорта пользователь не получает устойчивого ответа, как вернуться к проекту, отличить оригинал Excel от созданной базы и найти восстановимую копию.

**Критерий исправления.** Стартовый экран показывает недавние проекты и подключения по полному пути, тип источника и последний безопасный статус. Есть действие «Показать файл/каталог копий». Список хранит только пути и несекретные метаданные; отсутствие файла не создаёт новый и не удаляет запись молча.

## Рекомендуемый порядок исправления

1. Разделить first-run по намерению и прекратить создание default DB до выбора.
2. Жёстко классифицировать managed project и ordinary SQLite до любого write.
3. Добавить единый мастер Excel/CSV → новый проект с preview итоговых значений.
4. Сделать преобразования NULL/пустоты/leading zeros и режим append видимыми и восстановимыми.
5. Утвердить product storage/backup policy, независимую от versioned EXE и наличия D:.
6. Затем добавить recent items и расширять поддерживаемые форматы/провайдеры. MySQL/MariaDB, SQL Server и импорт в внешние таблицы сейчас не реализованы; onboarding не должен обещать их до соответствующих provider-срезов.

## Минимальная сквозная приёмка будущего onboarding

- На чистом профиле закрытие первого экрана не создаёт БД.
- XLSX с двумя листами, формулой, датой, `00123`, пустой и пробельной ячейками до commit показывает точный scope и все преобразования; исходный SHA-256 не меняется.
- Создание нового проекта в выбранном новом пути атомарно; существующий файл не меняется.
- Ordinary SQLite, пустой SQLite и managed project классифицируются отдельно; ошибочный выбор не меняет SHA-256.
- Повторный импорт явно показывает append и возможные дубли; отмена preview не меняет проект; ошибка посередине не добавляет часть строк.
- После успешного импорта доступен проверенный batch-undo либо именованная копия с понятным restore.
- Перезапуск новой версии находит те же пользовательские проекты независимо от каталога EXE; portable mode проверяется отдельно.
- PostgreSQL/SQLite открываются без автоматической установки сервера, миграции или копирования данных; права записи включаются только явно для конкретного подключения.
