# SmartSQL Experience: дизайн и UX

**Статус: целевая спецификация; не скриншот существующего приложения.** SmartSQL должен сочетать **организованность профессиональной DB IDE** и **спокойствие/простоту лучших массовых продуктов**. Это не «сделать DBeaver с другим цветом». Мы не переносим чужие макеты, иконки, тексты, изображения или точную визуальную композицию.

## 1. Референсы по принципам, не пикселям

| Продукт / источник | Берём общую идею | Не копируем |
|---|---|---|
| DBeaver Lite | Сценарии IDE: navigator → table/SQL → results/metadata; read-only explorer, фильтры, ERD | Eclipse-layout, конкретные панели/пиктограммы/проприетарные компоненты |
| VS Code | Приоритет контента, независимые вкладки, keyboard command palette и поиск | Цвета, activity-bar геометрию, меню и хоткеи 1:1 |
| Linear | Информационная насыщенность с тихой навигацией, фокус на содержимом и без визуального шума | Отличительные формы, тени, иконки, exact spacing |
| Notion | Понятное редактирование таблиц и управление видимыми колонками/представлениями | Notion-термины «страницы», карточки и UI-потоки целиком |
| Microsoft Fluent 2 / Apple HIG | Иерархия, адаптация под ОС, доступность, предсказуемая обратная связь | Фирменные визуальные элементы и trademark |

Официальные страницы в [REFERENCES.md](REFERENCES.md). Ориентир один: человек **без SQL** должен понимать, как открыть таблицу и исправить ошибку, а эксперт — получать все нужные инструменты без лишних диалогов.

## 2. Визуальная идентичность: продолжение текущей, не редизайн с нуля

В SmartSQL **уже существуют** семантические tokens [Tokens.axaml](../../src/SmartSQL.Desktop/Styles/Tokens.axaml), два режима темы и векторный бренд. Сохранять зелёную S-эмблему, согласованные цвета, явные системные оконные кнопки, русскую локализацию и Simple/Advanced. Не заменять Avalonia 12 сторонним стеком ради «красоты».

Фактическая **Light**: canvas `#F5F2EB`, surface `#FAF9F6`, border `#D2CEC5`, text `#252C32`, accent `#245E48`; фактическая **Dark/Gray**: canvas `#23262B`, surface `#2D3035`, text `#F1F2F4`, accent text `#9BD4B5`. Не объявлять новые цвета принятыми без контрастных тестов. Темы в текущем коде названы Light/Dark, хотя UI описывает «светлая/серая»: терминология для пользователя должна быть последовательной.

Текущие corner `UiCardRadius=10`, `UiControlRadius=8`, размеры `8/12/20`, page padding `24,20`. **Предложение**, требующее проверки на экране: один общий spacing rhythm 4/8/12/16/24, controls по плотности Comfortable/Compact, table row height 34–38 в Comfortable и 28–32 в Compact, при DPI scaling без жёсткого clipping. Это *начальные гипотезы*, не обязательные пиксели: проверять с реальными строками, текстами и широкими таблицами.

### Визуальные правила

1. Одна явная главная задача на экран; основные действия не конкурируют с 10 равными акцентными кнопками.
2. 85% площади таблицы/SQL по возможности отдавать полезным данным; точная величина — UX-гипотеза, не release metric.
3. Профессиональные функции **доступны, но не навязаны**: secondary toolbar/menu/inspector.
4. Выделение, hover, focus, disabled, loading, success, warning и danger различимы **не только цветом**.
5. Текстовые метки первичны; icon-only кнопки только в понятном контексте, tooltip + accessible name.
6. Значения NULL, пусто, false, 0, ошибка, read-only — визуально различимы.
7. Микроанимации 100–180мс только если не мешают набору данных/доступности; reduced motion отключает их. Не жертвовать скоростью из-за декоративного blur.
8. Не «стекло на всё окно»: лёгкая глубина/разделители, без слепящих градиентов, тяжёлых теней и разноцветных панелей.

## 3. Предлагаемая информационная архитектура

Три **пользовательские** области: **Источники**, **Работа**, **Информация**.

```text
┌────────────────────────────────────────────────────────────────────┐
│ S SmartSQL     [Поиск команд, таблиц…]     [Светлая/Серая] [Режим]  │
├───────────────┬────────────────────────────────────────────────────┤
│ ПРОЕКТЫ       │ [Клиенты] [Заказы] [SQL: Анализ]                x  │
│  • Мой проект │────────────────────────────────────────────────────│
│ ПОДКЛЮЧЕНИЯ   │ Клиенты          [Поиск] [Фильтр] [Столбцы] [•••]   │
│  • Продажи PG │  База: Продажи / public       Только чтение        │
│  • Локальная  │ ┌──────────────────────────────────────────────┐   │
│               │ │ ID  Имя      Статус       Дата              │   │
│ + Открыть     │ │ ...                                           │   │
│ + Подключить  │ │                                             │   │
│               │ └──────────────────────────────────────────────┘   │
│               │ [100 строк]  [Страница 1]  [Обновить]              │
├───────────────┴────────────────────────────────────────────────────┤
│ ● Сохранено локально   │ PG: подключено │ 100 / неизвестно строк │
└────────────────────────────────────────────────────────────────────┘
```

**Это собственный концептуальный wireframe, не код/готовая вёрстка.** Real shell сейчас реализован WorkspaceWindow: расширяем его, не создавая второе основное окно.

- Левая колонка: названия источников и типы, сортировка, поиск, разворот и recent; «Проект SmartSQL» отличается от «Подключение к чужой БД». Не показывать необъяснимые GUID/номера.
- Центральная часть: tab bar, контекстный заголовок, контекстные действия, таблица либо SQL/диаграмма. Приоритет активной вкладки; несколько источников с одинаковыми table names должны быть различимы.
- Правая панель: *скрытый по умолчанию* «Сведения / Значение / Свойства», открывается по требованию или при выборе длинного значения; не занимает ширину таблицы постоянно.
- Нижний status: коротко и проверяемо — источник, read/write/transaction state, запрос/строки, локальная сохранность, операции/ошибки. No false success.
- Вертикальные вкладки и docking как в IDE — **после** улучшения основных сценариев, не раньше UI-приёмки.

## 4. Простое начало без SQL

Первый экран SmartSQL, если ещё нет осмысленно выбранного источника:
1. Большая основная карточка **«Начать с Excel или CSV»**.
2. Соседняя **«Создать локальную базу»**.
3. **«Открыть существующую базу»**: файл SQLite/SmartSQL либо серверное подключение.
4. Ниже «Недавно открытые», «Где хранятся данные?», «Как подключиться к PostgreSQL».
5. Демопроект — *только явно открытый пример*, не автоматически создаваемый рядом с пользовательскими данными.
6. Пока M05 не готов: восстановление не обещать готовым; disabled с объяснением/не показывать пока функцию нельзя выполнить.

Принцип: каждое действие начинается с намерения человека, не с диалога «Создать таблицу», когда ещё не выбрана БД. Существующий файл никогда не принимается как новый проект через скрытую инициализацию.

## 5. Главные пользовательские сценарии

### S1. Пользователь Excel → БД
Файл → выбор листа/диапазона/заголовков → таблица preview «исходно / будет сохранено» → типы/ошибки/количество строк → путь новой БД → явная кнопка создания → готовая таблица + сообщение «оригинал Excel не изменён». Не обещать перенос формул/форматирования/макросов. Preserve identifiers with leading zeros and typed empty/null diagnostics.

### S2. Подключение внешней БД
«Подключить» → движок с кратким объяснением → endpoint/path, TLS/auth, кнопку «Проверить» → показывать роль, read-only/write coverage → открыть дерево; пароль на сессию без хранения либо opt-in safe vault позже. Недоступный сервер — не пустая БД.

### S3. Редактирование ячейки
Двойной клик → editor, соответствующий native type → визуальная метка несохранённого значения, проверка/предпросмотр → commit/ошибка/конфликт → перечитать строку. Не смешивать «выделил» и «сохранил», не переиспользовать устаревший edit handle, не повторять неизвестный COMMIT.

### S4. Запрос без SQL
«Найти данные» → таблицы и поля → визуальные правила, сортировка/объединение подтверждённых данных → текст SQL под спойлером → выполнить SELECT → таблица результатов; unsupported predicate чётко объяснён. Builder не симулирует поддержку всего SQL.

### S5. Работа эксперта
Ctrl/Cmd+K → «Открыть SQL» → tab с выбранным соединением/схемой → editor, autocomplete, run selection, результаты/ошибки/metadata. DML/DDL только после отдельного transaction-policy и осязаемого предупреждения, «закрыть вкладку» не должно тайно подтверждать изменения.

### S6. Защита/история
История (лог просмотра/действий), Отмена (доступная обратимая операция), Копии (проверенные snapshots), Отмена транзакции (DB rollback) — **четыре разных действия**. Для каждого тип, область, источник, статус, обратимость. «Удалить запись истории» не означает «удалить результат DB update».

## 7. Компоненты и интерактивные состояния

**Buttons:** один primary на диалог, secondary/cancel, destructive с точным объектом. Disabled поясняет причину через текст и tooltip. **Fields:** label над input, пример, validation рядом с полем; пароль скрыт, reveal по желанию, никогда в message/log. **Table:** sticky header, виртуализация, отдельный row handle, keyboard navigation, контекстные действия, horizontal scroll без блокирования удаления столбцов. **Dialogs:** размеры по содержимому, scroll region отдельно от footer, ESC уважает незавершённый commit. **Tabs:** несохранённый значок, смена соединения не «перекидывает» запрос на другой источник.

**Every async screen:** idle → loading (progress/cancel) → ready / empty / permission denied / error / disconnected / ambiguous result. В ошибке всегда «Что случилось?», «Что сохранено?», «Что можно сделать?». Обязательные случаи: server offline, wrong TLS certificate, file missing, readonly table, row conflict, broken backup, disk full, cancel after commit response unknown.

**Подсказки** контекстные и короткие: рядом с действием, с возможностью открыть объяснение, не tour overlay на каждом шаге. **Командная палитра** — дополнительный путь, а не единственный способ найти функцию.

## 8. Два уровня плотности, не две программы

Simple: понятные глаголы «Открыть», «Изменить», «Фильтр», «Столбцы», «Сохранить», большая рабочая таблица, нет шумного SQL toolstrip. Advanced: SQL, планы, свойства, shortcuts, дополнительные toolbar sections, но общая структура и идентичность источников те же. Переключатель не скрывает несохранённую операцию и не меняет permissions.

Предлагаемые density presets Comfortable/Compact — **независимы** от Simple/Advanced и Theme. Вводить только если UX подтверждает пользу, хранить отдельную настройку и не ломать нынешние файлы настроек.

## 9. UX acceptance / измерения

- 5 из 5 тестовых сценариев Excel-first выполняются без написания SQL, без подсказок разработчика, без потери исходного файла. Тестировать хотя бы с пользователями, которые не знают баз данных, а не только автором проекта.
- В каждом состоянии пользователь может назвать **текущую БД, режим доступа, сохранённость** после просмотра экрана.
- Zero overlap в диалогах для 100/150/200% Windows scaling и маленького окна; две темы, keyboard-only, Tab/Shift+Tab, Esc, Enter, Ctrl/Cmd+K.
- Screen reader: таблица, column names, selection, focus, error statuses и icon-only действия имеют accessible labels и предсказуемый порядок.
- Performance профили: начальный запуск/скролл/смена вкладок на синтетических таблицах с большими данными; реальные целевые бюджеты фиксировать после baseline, не придумывать FPS/мс без замера.
- Подтверждать look&feel со скриншотами каждого критичного экрана и независимой проверкой, не «красиво по мнению Codex».
- Полная ручная приёмка и package smoke — отдельны от unit/xUnit.

## 10. Практический путь внедрения

**Pass A: visual audit** текущего `WorkspaceWindow`, `MainWindow`, 6 UF09 экранов, screenshot matrix, контраст/spacing audit без изменения данных. **Pass B:** семантические tokens + одинаковые состояния/controls, без редизайна навигации одномоментно. **Pass C:** welcome, понятные tree labels, колонка и boolean UI, scroll overlap. **Pass D:** advanced workspace, query builder и ERD в существующих tab contracts. Для каждого экрана отдельный PR/acceptance. Режим/тема переключаются без потери набранного SQL и транзакции.
