# M01.04 — подключение хранилища к запуску

17 октября 2026: **код/автотесты/review готовы, ручная UI/clean-PC приёмка открыта**. Принятая product policy — D056/[PRODUCT_STORAGE](PRODUCT_STORAGE.md). Миграция прежних root — отдельный M01.05, расширенная race/path matrix — M01.06. Пользователь запросил после этого среза самостоятельную проверку: [инструкция](USER_TEST_M0104.md); до её результатов не переходить автоматически к следующему изменяющему storage срезу.

## Что теперь исполняется

`Program` разрешает хранилище до Avalonia. `WorkspacePaths` держит один `StorageRuntimeLease` до завершения процесса; последующие обращения получают сохранённый путь. `App` загружает тему и создаёт WorkspaceWindow/default managed project только после успешной проверки. Ошибка выбора показывает отдельное окно с native caption buttons, причиной, обычным повтором, выбором существующего хранилища только для этого запуска и выходом. Неправильный выбор в picker не подменяет исходный retry target. Внизу рабочего окна виден копируемый путь хранилища.

Порядок прежний D056: present env override (empty/relative = ошибка) → explicit portable marker рядом с EXE → installed bootstrap + совпадающий root marker → ограниченный поиск старых root → только подтверждённый first use. Высокий приоритет не проверяет/не создаёт нижний. Внешние SQLite/managed проекты остаются на выбранных пользователем путях, PostgreSQL остаётся серверным.

`StorageRuntimeRoot` повторно использует pure selector и read-only metadata helpers. Реальная стадия проверяет том/родительские каталоги, file-as-directory, UNC/device/mapped network, reparse dirs/metadata files, расположение вне app и D:-ограничение разработки. Известные legacy кандидаты — `<EXE>/data/local`, `<EXE>/run-data/local`, для `<build>/app` также `<build>/run-data/local`; поиск не рекурсивный. Неизвестный непустой explicit root без marker не принимается. Missing installed root не создаётся заново. Marker future/mismatch/ошибки чтения — отказ, без fallback и новой БД.

Новый root получает GUID marker через CreateNew + Flush(true), без overwrite. Installed bootstrap пишется в уникальный temp, Flush(true), File.Move(overwrite:false). Root-only write probe использует DeleteOnClose; до root marker не создаются дочерние temp/cache. После marker подготавливаются temp/cache/dotnet-bundles; bootstrap публикуется только после этих проверок. Поздний сбой может оставить проверяемый orphan marker, но не создаёт активную БД и не принимает сироту молча. Повреждённый/частично записанный marker сохраняется и требует явного восстановления, не автоматического ремонта. Bootstrap recovery/migration остаются ограниченными, M01.05 не выполнен.

Межпроцессный selection mutex сериализует первый installed выбор (ожидание до 10 секунд и перечитывание). Root mutex держится весь запуск; второй Desktop для того же canonical path получает отказ. На Windows используется `Global\` namespace, чтобы не ограничивать lock одной RDP/session; GUID/path hash не является проверкой владения каталогом. [Win32 namespaces](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces) подтверждает различие namespace; отдельный live RDP-проход не выполнялся. Mutex освобождается на том же main/UI thread; abandoned mutex ведёт к повторной проверке файлов, не к разрешению на восстановление по умолчанию.

Process TEMP/TMP/TMPDIR/cache/bundle variables назначаются только после открытия lease; при ошибке выполняется rollback, настройки пользователя/системы не меняются. ThemePreferences сохраняет public D:-guard для прямых dev/test paths; CreateDefault использует только уже проверенный runtime root и допускает product LocalApplicationData. Debug и workspace-launched builds используют development policy на D: либо явный отказ; release default не ищет SmartSQL.sln. Чистый конечный ПК без D: пока не принят на VM.

`Run-Published.ps1` больше не выбирает `run-data/local` и не создаёт папки: без явного -DataDirectory запускает обычный resolver приложения, с ним передаёт только проверенный D:-override. Это всё ещё D:-ограниченный dev/test helper; обычному EXE PowerShell не нужен. `Publish.ps1 -PortableDataDirectory` создаёт явный marker **до manifest/hash/ZIP**, не создавая целевой root. Для пользовательской preview.9 root — `D:\Code\SmartSQL-user-tests\m0104`, вне версий/исходников. Без этого параметра marker не добавляется.

## Доказательства и ограничения

Full Debug `scripts/Build.ps1 -NoRestore` + `scripts/Test.ps1 -NoBuild -NoRestore`: **771 passed / 0 skipped / 0 warnings/errors** (Domain 1 / Application 144 / Infrastructure 492 / Desktop 134), **60 real PostgreSQL facts**. TRX `.workspace/test-results/*2026-10-17_22_35_11*.trx`. Owned PG 17 на loopback 15432 штатно остановлен. 17 новых cases: 13 FS/lifecycle cases + 4 реальных child-process tests; reparse creation cases зависят от поддержки/прав тестового хоста и не являются полной M01.06 acceptance.

Test-only console project `SmartSQL.Storage.Probe` строится через test ProjectReference, не входит в Desktop publish. Synthetic D:-процессы проверяют competing init/один bootstrap, второй активный root, kill+reopen с сохранением идентичности, kill до marker (пустая папка допускает новый старт), kill после marker до bootstrap (orphan отказ). Тестовые callback checkpoints — trusted in-process hooks, не флаги из JSON/env пользователя. Все child processes завершаются, собственные fixtures удаляются. Это не проверка всех аппаратных power-loss состояний/FS durability.

Независимый source review нашёл и помог исправить unused installed-base validation, pre-marker temp window, session-local mutex, незафиксированный retry target и rollback process env. Финальное ограниченное review блокеров не нашло. Computer Use снова отказал при initialization (kernel assets/path/os error 3); новая ручная UI/DPI/Narrator/реальный no-D VM/EXE-vs-launcher приёмка **не объявляется пройденной**. Авторизованных пользовательских данных на C: не создавали, прежние root не принимали/не переносили.

Остаток: M01.05 copy-first old-root migration, M01.06 handle/TOCTOU/path alias/ACL/full-disk/long-path matrix, RDP/clean-PC acceptance и текущие T04/T11/T12/T23. Канонизация имени/Global mutex не защищает от всех физических aliases и внешней подмены после проверки; это не OS sandbox. Автоматический default managed проект в WorkspaceWindow пока остаётся прежним поведением до M03 onboarding. Новых cloud/AI/DBMS/write permissions/installer этим срезом нет.
